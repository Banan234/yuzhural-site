# Выпуск, откат и мониторинг

Выполняйте одну операцию deploy/rollback/restore за раз. До операции проверьте
резервную копию данных и доступность нужных локальных образов; rollback не
собирает и не скачивает отсутствующий образ автоматически.

```bash
cat deploy/state/production-release.env
./deploy/deploy-release.sh --env-file /etc/yuzhural-site/production.env
```

Состояние записывается через временный файл и rename. `in_progress` и `failed`
не означают рабочий выпуск. `ATTEMPTED_RELEASE_TAG` и `LAST_DEPLOY_PHASE`
показывают попытку и её этап (`build`, `up`, `catalog`, `smoke`, `complete`).
После начала `up` поле `LIVE_RELEASE_TAG` пусто до успешного окончания проверок:
частично заменённые контейнеры не считаются проверенным выпуском.
`LAST_GOOD_RELEASE_TAG` меняется только после подготовки каталога и smoke;
повторный выпуск того же тега не затирает предыдущий рабочий тег.

После неудачной/прерванной попытки команда без тега выбирает last-good.
После успешного выпуска она выбирает previous-good:

```bash
./deploy/rollback.sh --env-file /etc/yuzhural-site/production.env
```

Явный выбор (при наличии совместимого образа):

```bash
./deploy/rollback.sh --env-file /etc/yuzhural-site/production.env --tag <good-tag>
```

Оба скрипта выполняют `up`, подготовку HTML и smoke. Ошибка любого этапа
возвращает ненулевой код и сохраняет историю рабочих тегов. Автоматического
отката после неудачного deploy нет: изучите фазу и выполните rollback отдельно.
SIGKILL/потеря питания могут оставить `in_progress`; это тоже не success.

## HTML и данные

После запуска выбранного web его `index.html`, `.vite/manifest.json` и полный `server/` SSR bundle
извлекаются в временный каталог общего data mount. Под существующей блокировкой
импорта новый комплект HTML всех товаров и конечных листов каталога генерируется из **текущего** активного
JSON. Обновляются ссылки `data/catalog-current` и `data/web-template-current`.
При ошибке подготовки старые ссылки сохраняются; при отказе второй установки
первая возвращается назад. Не удаляйте эти ссылки и скрытые release-каталоги.

Шаблон кода хранится отдельно от выпуска каталога, чтобы последующие импорты
(в том числе после отката) использовали assets и SSR выбранного web.
Каталог, категории и их обычная пагинация обновляются в том же выпуске;
устаревшие листы удаляются, а отсутствие активного HTML возвращает 404.
Поиск/фильтры/сортировка используют loading HTML с noindex.
Отсутствующий или неполный SSR bundle блокирует подготовку до смены указателей.
`PRERENDER_TEMPLATE_DIR=/app/data/web-template-current` задан в compose.
Smoke проверяет полный набор HTML, ссылки по manifest и HTTP/MIME всех manifest
assets через `http://web`; одного ответа 200 с HTML вместо JavaScript недостаточно.

Откат **не возвращает старые цены/остатки**: меняются код и HTML, сохраняется
последний каталог, включая pending. Восстановление данных — отдельная операция
по `docs/catalog-retention.md`; после неё HTML надо заново подготовить под
выбранный web до признания выпуска рабочим. Старый образ должен поддерживать
текущую схему каталога, pending и существующие prerender/importLock модули.
Отсутствующий manifest или несовместимый renderer останавливает операцию.

Между `up` и окончанием подготовки возможно краткое рассогласование HTML/assets.
Это не схема без простоя. При отказе подготовки сервис требует rollback;
скрипт не помечает такое состояние успешным. Прямой `docker compose up` обходит
подготовку и не является эквивалентом штатного выпуска. Для старых уже открытых
вкладок сохранение предыдущих assets не гарантируется.

## Мониторинг

```bash
./deploy/run-health-monitor.sh --env-file /etc/yuzhural-site/production.env
```

Wrapper читает указанный env и передаёт monitor-параметры в работающий app.
Значения токенов/webhook не помещаются в argv. Для обязательных форм задайте
`MONITOR_REQUIRE_FORMS=true`; отключённые формы иначе допускаются контрактом.
State (`MONITOR_STATE_FILE`, по умолчанию `data/monitor-state.json`) должен быть
на сохраняемом data mount. Один неизменный подтверждённый сбой отправляется
один раз; восстановление и новый сбой — отдельные события. Неуспешная отправка
остаётся pending и повторяется; при ней даже здоровый monitor возвращает exit 1.
HTTP 2xx с `ok:false` не считается подтверждением доставки. HTTP-ack webhook
не доказывает получение сообщения человеком. Монитор внутри app не наблюдает
полностью недоступный app/host; для этого нужна независимая проверка.

Локальные проверки 27.10.2026 выполнены с подставным Docker, настоящим native
Nginx и loopback webhook. Реальные Docker volumes/UID, tar/exec, Node 20,
исторические образы и внешний сервер ещё требуют изолированной приёмки.
