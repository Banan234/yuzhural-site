# Хранение резервных копий и выпусков каталога

## Резервные копии

Перед публикацией импорта создаётся снимок данных. После успешного создания
снимка остаются 14 последних завершённых резервных копий. Число задаётся
`BACKUP_RETENTION` (по умолчанию 14); это количество снимков, а не дней.
Проверка неизменившегося прайса резервную копию не создаёт.

Очистка удаляет только завершённые копии с читаемым manifest.json из BACKUP_DIR
(по умолчанию data/backups). Незавершённые и посторонние каталоги автоматически
не удаляются. Если создание новой копии не завершилось, старые копии не очищаются.

Новые копии используют manifest v2: активный `data/catalog-current` разрешается
в конкретный выпуск и целиком сохраняется как `catalog-release`, включая
`public` (price, sitemap и HTML). `BACKUP_INCLUDE_PUBLIC=false` исключает только
отдельный legacy-каталог `data/public`; на полноту активного выпуска не влияет. Перед восстановлением проверить manifest, размеры
и SHA-256 командой npm run backup:verify -- <идентификатор>.

## Выпуски каталога

После успешной транзакции публикации сохраняются три последних выпуска в
`data/.catalog-current-releases` и активный выпуск, если он не входит в эти три.
Ссылка `data/catalog-current` определяет активный выпуск; он никогда не удаляется
этой очисткой. При ошибке публикации действует откат транзакции.

Полные выпуски и резервные копии имеют разное назначение: выпуск содержит
готовый каталог и публичные артефакты, резервная копия — снимок данных перед
обновлением. Удалять один вид хранения вместо другого нельзя.

## Отчёты и локальные материалы

Архивы HTML/JSON-отчётов хранятся 30 дней; связанные с неотправленными письмами
отчёты сохраняются до отправки. Очередь писем, текущий отчёт и состояние импорта
не удаляются по возрасту. Ежедневная очистка отчётов не затрагивает резервные копии
и выпуски каталога: у них отдельные правила выше.

Архивы, локальные состояния и рабочая папка outputs исключены из Docker build
context. Это не удаляет файлы на машине и не заменяет перенос необходимых
runtime-данных на сервер при развёртывании.

## Безопасное восстановление

Остановить приложение, планировщик и прочих писателей runtime-данных. Создать
копию на отдельном носителе; локальная retention не заменяет внешнюю резервную
копию. Для первой проверки использовать изолированную копию проекта и данных.
Не выполнять restore поверх рабочего сервера ради проверки.

В изолированном окружении: `npm run backup:verify -- <id>`, затем
`npm run backup:restore -- <id>` (проверка без записи), затем та же команда
с `--apply`. Перед применением сверяются размеры/SHA-256, файлы копируются во
временную папку на файловой системе назначения и повторно проверяются.
Выпуск переключается последним через существующую атомарную ссылку; ошибки
установки откатываются существующей транзакцией. Legacy products/registry/price
синхронизируются из активного снимка, если соответствующие файлы в нём есть.

Backup и restore делят блокировку с импортом. Встроенная копия импортера
использует уже взятую им блокировку. Эта блокировка не останавливает запись
заявок/чата: для согласованного снимка этих данных приложение надо остановить.
Это не гарантия crash consistency при отключении питания.

Старые v1/legacy-копии проверяются и восстанавливаются в legacy-окружение, но
restore при существующем `catalog-current` запрещён, если копия не содержит
активного выпуска. Целевой `catalog-current` должен отсутствовать либо быть
symlink. Если это физический каталог, сначала остановить сервис и перенести
его в отдельное безопасное место; автоматического удаления/миграции нет.

После восстановления проверить каталог новым и уже запущенным потребителем,
а также price/sitemap/HTML через active path; затем перезапуск и повторную
проверку. В Docker повторить с постоянным data mount и публичной выдачей Nginx.
Хранить копии с ограниченным доступом: они могут содержать приватные данные.
Приватные стандартные пути chat-store, forms-outbox и consent-evidence исключены
из Docker context. Нестандартные пути из env нужно хранить вне context либо
добавлять в `.dockerignore` отдельно.

## Согласованность подготовки каталога

Обычный импорт всегда готовит полный product HTML рядом с JSON, price, sitemap
и redirects в новом выпуске. Отсутствующий/повреждённый шаблон, неполное покрытие
или коммерческое расхождение HTML/JSON-LD с JSON прерывают подготовку до active
switch. `PUBLIC_ARTIFACTS_DIR` больше не включает/отключает генерацию HTML.
Перед обычным импортом нужен шаблон `dist/index.html` либо
`PRERENDER_TEMPLATE_DIR/index.html`; API-образ получает его из build-stage.
Dry-run по-прежнему не готовит/не публикует выпуск.

`npm run build:prod` удерживает общую блокировку импорта/backup/restore на всех
шагах. Prerender и runtime-sync используют активный выпуск, если он существует;
при отсутствии active — legacy bootstrap. Сломанная active-ссылка не разрешает
тихий переход к legacy. Runtime-sync готовит весь новый `data/public` отдельно,
проверяет JSON/sitemap/HTML и устанавливает каталог после успешной подготовки.
Это заменяет read-only redirects без изменения прав исходника и сохраняет
прежний output при ошибке подготовки/установки. Прямой sync не должен запускаться
параллельно с импортом; штатная build:prod обеспечивает эту блокировку.

Dockerfile переносит сгенерированный полный публичный fallback в web/API-stage;
клиентский build по-прежнему ограничивает SSR-карточки, runtime fallback содержит
весь набор. Это увеличивает публичную часть образов; фактические размеры и
контейнерные права требуют проверки Docker build. Приватные runtime-пути из T00
в эти генерируемые каталоги не копируются.

Обновление кода само по себе не исправляет уже существующий неполный выпуск:
сначала репетиция импорта/восстановления на изолированном стенде, затем отдельное
разрешение на рабочую публикацию. После согласованного изменения (§20 отчёта) наличие active products.json
отключает fallback для карточек: отсутствующий HTML возвращает 404. При bootstrap
без active products.json (включая пустую папку из Dockerfile) fallback сохраняется.

### Частичный выпуск и восстановление (2026-10-27)

Pending-карточки хранятся в том же `products.json` активного выпуска, с
`dataStatus=pending` и пустыми коммерческими полями. Они резервируются и
восстанавливаются вместе с JSON/HTML/реестром и исходным XLS; отдельной базы
карантина для обслуживания карточек нет. Отчёт содержит sourceDisposition.
Восстановление должно проверять реальный consumer: pending-карточка остаётся
без цены/покупки, а корректная читает цену восстановленного выпуска.
