# Подтверждённое наполнение карточек каталога

Постоянная инструкция: [CATALOG_ENRICHMENT_POLICY.md](../CATALOG_ENRICHMENT_POLICY.md).
Первый пакет — 12 явно перечисленных SKU базового АВВГ, ревизия
`2026-11-12.avvg-pilot.1`. Второй пакет — 12 SKU ВВГнг(А)-LS в области `scope-family-0001-hka-LS`.
Общая ревизия `2026-11-12.avvg-vvg-ls-pilot.2`. Ограничения ниже описывают исторические пакеты. Для новых групповых правил действует политика 2.1 с допуском по отдельному свойству.

`data/catalogEnrichment.json` хранит точечные редакционные решения, источники,
SHA сохранённых HTML, применимость каждого факта, уверенность, результаты
проверки маркировки, незаполненные поля и историю. Это дополнение к существующим
`family-0002` / `hka-family-0002`, без своей классификации или декодера.
Изготовитель источника не присваивается складской позиции.

`lib/catalogEnrichment.js` проверяет SKU, отпечаток исходного обозначения и
значимых технических полей, семейство, правило и ревизию конструктивного
доказательства. Pending, несовпадение или конфликт блокируют наполнение.
Другие SKU, в том числе похожие, не получают данные. Наличие ручного текста
сохраняет его; заменяется только пустое описание, точный результат существующего
`buildDescription`. Текст из `descriptions` используется через `descriptionRef`
при совпадении правила конструктивного доказательства. Один текст может
обслуживать несколько явно перечисленных SKU. Записи с собственным `description`
поддерживаются для проверенных исключений. Существующее
несовместимое значение характеристики сохраняется, решение возвращает `conflict`.

Чтение подключено только в `prepareProductDetail`, общей для API и prerender.
Входы поиска, фильтров, группировки предложений и компактного каталога остаются
прежними. Поля прайса, коммерция и изображения не записываются. В карточку
попадают лишь разрешённые технические поля и описание; provenance не добавляется
в API. ГОСТ/ТУ из прайса не извлекаются и не публикуются этим механизмом.

Импорт регенерирует `products.json`, но не редактирует этот файл решений.
Следующий вызов подготовки карточки повторно применяет подтверждённые факты к
новому товару с прежней совместимой идентичностью. Перезапуск сервера загружает
изменённый файл решений; новый SSR использует его при обычной сборке/импорте.
Уже выпущенные HTML автоматически не переписываются. Пилот не выполнял рабочий
импорт, переключение active release, сборку в `dist`, push или deploy.

Проверка: `npx vitest run lib/catalogEnrichment.test.js`.
Временная фикстура дважды пересоздаёт записи штатными функциями импорта,
назначает идентичности из копии реестра, заменяет временный `products.json`,
сравнивает работающий и новый consumer и повторно формирует HTML. Это не полный
запуск CLI импорта: не проверяет сеть прайса, блокировку, транзакцию переключения
выпуска, письма или восстановление backup. Их бизнес-логика не менялась.

Локальный отчёт: `outputs/catalog-enrichment-pilot-2026-11-12/report.html`.
Рендеры и исходники источников лежат рядом; это внутренние материалы, не
публичная часть сайта. Перед расширением этого пилота требовались согласование, разбор
неизвестных параметров и отдельные области для нг/LS/плоских/разноразмерных
исполнений. Не переносить низковольтные характеристики на среднее напряжение.

Отчёт второго пилота — `outputs/catalog-enrichment-pilot-2-2026-11-12/report.html`.

## Первая ограниченная партия

Ревизия `2026-11-12.batch-1` добавляет 120 явных решений. В каждом новом
решении `factProfileRef` указывает на общий набор фактов в `factProfiles`.
Набор применим только при совпадении идентичности SKU, семейства, правила и
ревизии доказательства и полной документированной расшифровке. Ссылки на
источники хранятся у фактов. Существующие записи с собственными `facts`
продолжают работать. Плоские, экранированные и специальные варианты не
получают характеристики по сходству названия.

Поиск записи использует индекс неизменяемого снимка. Повтор SKU блокирует обе
записи. Для отката отдельного решения убрать запись SKU или изменить её статус
и перечитать снимок при перезапуске. Общий набор фактов и текст сохраняются,
пока на них ссылаются другие SKU. При продолжении после остановки готовить
следующую партию от актуального снимка, проверяя список SKU, правило и данные
снова перед заменой реестра. Изменившийся активный выпуск требует новой проверки
совместимости, а произвольные правки реестра требуют сверки перед записью.

Аудит, журналы, проверка 19 полей и предпросмотры находятся в
`outputs/catalog-enrichment-batch-1-2026-11-12/report.html`.

## Вторая ограниченная партия

Ревизия `2026-11-12.batch-2` добавляет 393 явных решения и 21 профиль.
У новых общих наборов дополнительно проверяются точная складская марка и
отсортированные атрибуты. Описание привязано к тому же набору фактов. Это
различает, например, HF и FRHF, которые могут иметь один конструктивный код.
У МКЭШ наличие и материал экрана опираются на точную марку и заводские
описания, а не на флаг отдельного индекса в разборе размера.

Отчёт и локальные предпросмотры — `outputs/catalog-enrichment-batch-2-2026-11-12/report.html`.

## Дополнительное исследование 537 SKU

Ревизия `2026-11-13.followup` сохраняет тот же список SKU. Поля
`Напряжение` и `Класс гибкости` добавляются только в характеристики
детальной карточки. Профиль может ограничить отдельный факт массивом
`sections` с точными сечениями в мм². Это дополнительная проверка после
сверки идентичности SKU и конструктивного правила. Для фактов без массива
сохраняется область действия профиля.

Локальный отчёт — `outputs/catalog-enrichment-followup-2026-11-13/report.html`.

## Аудит применимости к SKU

Ревизия `2026-11-13.reliability` допускает к отображению только факты со
статусом `CONFIRMED` и категорией A или B в `reliability`. Категория C хранит
найденные для отдельных заводов значения со статусом
`ONLINE_UNVERIFIED_FOR_SKU`. Конфликт категории D хранится со статусом
`CONFLICT_UNRESOLVED`. Прежние значения и источники сохраняются в реестре.
Узкие поправки к публичному тексту расшифровки для проверенных SKU задаются
через `markingReview.detailCorrections` в том же реестре.

[Отчёт и снимок для восстановления](../outputs/catalog-enrichment-reliability-2026-11-13/report.html).

## Покупательское наполнение (политика 2.0)

`contentProfiles` и `contentAssignments` в том же реестре хранят редакционные
блоки отдельно от технических фактов. Профиль допускается только при совпадении
складской идентичности и семейства из действующего декодера и при разборе без
предупреждений. Для ранее проверенных технических записей также действует их
защита от конфликтов. Редакционные сведения используются во вкладке описания,
при этом `product.description`, используемое существующей SEO-механикой,
сохраняется. Источники остаются в реестре и локальном отчёте.

[Отчёт наполнения](../outputs/catalog-content-2026-11-13/report.html).
