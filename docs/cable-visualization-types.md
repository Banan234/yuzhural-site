# Типы визуализации кабелей

`visualProfile.visualizationType` — производное правило композиции:

| Значение              | Композиция                                               |
| --------------------- | -------------------------------------------------------- |
| `SIMPLE`              | Объёмное раскрытие жил известной простой конструкции     |
| `MULTICORE`           | Компактный объёмный срез известного многожильного кабеля |
| `LAYERED`             | Ступенчатый разрез отдельных конструктивных слоёв        |
| `MULTICORE + LAYERED` | Компактный срез жил и ступенчатые слои одновременно      |
| `NEEDS_REVIEW`        | Недостаточные или противоречивые данные о конструкции    |

Состав комбинации доступен в `visualization.components`. Обоснование, причины
проверки и известные видимые слои находятся в `visualization` рядом с профилем.
Этот объект не является новым источником технических характеристик товара.

## Основание решения

Классификатор использует существующие `familyVisualRules`, `visualProfile`,
`technicalProfile` и незакрытые структурные вопросы классификации. Он не
определяет броню или экран по случайному вхождению буквы в названии.

В `data/cableVisualizationRules.json` задаются поддерживаемые конструкции,
виды брони/экрана, специальные элементы и порог компактного среза. Сейчас это
6 жил для известного круглого изделия с общей оболочкой. Порог определяет
композицию, а не инженерный термин «многожильный». Stranded описывает проволоки
внутри одной жилы и сам по себе не означает `MULTICORE`.

Броня, экран, огнестойкий барьер и явно известная внутренняя оболочка требуют
`LAYERED` независимо от количества жил. Парная, коаксиальная, оптическая или
иная конструкция без согласованной схемы остаётся `NEEDS_REVIEW`. СИП-4 с
подтверждённым пучком изолированных жил относится к `SIMPLE`, но сохраняет
геометрию `twisted-bundle` и требует собственного референса. Одиночные провода
и плоские изделия также сохраняют собственную геометрию.

`visibleLayerCount` считает только известные конверты, которые потребуются
иллюстрации: изоляцию жилы, общую оболочку, экран, броню и отдельные барьеры.
Контактный провод, число жил и проволоки меди не являются дополнительными
слоями. Это не полное число всех технологических слоёв: `physicalLayerCount`
остаётся `null`. Неизвестный невидимый заполнитель не создаёт выдуманную ступень
и сам по себе не блокирует известную простую конструкцию.

## Идентичность и ограничения

`visualizationType` исключён из хеша `visualProfileId` / `visualKey`: добавление
производной стратегии не инвалидирует утверждённые ключи или привязки. Все
прежние конструктивные поля продолжают участвовать в идентичности. Профили
с разными конструкциями не объединяются.

Тип визуализации не меняет `visualClassification`, не утверждает цвета и
исполнение конкретного SKU и не разрешает генерацию. Исторический production
plan/manifest и PNG не мигрируют автоматически. Prompt builder не изменён.

## Повторяемый dry-run

```sh
node scripts/auditCableVisualizationTypes.js --dry-run
```

Доступен только `--dry-run`; Image API, `.env`, генератор и публикация не
подключены. `--out outputs/<directory>` позволяет сохранить отдельный отчёт.
Инструмент записывает только отчёты внутри `outputs/` и проверяет SHA-256
каталога, PNG, metadata и привязок до и после работы.

В отчёте от 8 ноября 2026 сохранены два независимых среза:

- Запрошенные 5708 позиций: готовые профили из dry-run 16 октября, с исходными
  visualKey и техническими признаками. Только добавлен тип визуализации.
- Текущий каталог: заново классифицирован текущими правилами и парсером.
  Изменения состава и исходных ключей относительно истории не приписываются
  новому полю. Полный список отличающихся SKU находится в `catalog-delta.json`.

`report.html` содержит оба среза, фильтры, поиск, конкретные причины проверки и
предложения референсов. `needs-review.json` содержит все неоднозначные SKU
запрошенного среза. `reference-plan.json` — только кандидаты для следующего
согласования, без генераций. `integrity.json` хранит контрольные суммы.
