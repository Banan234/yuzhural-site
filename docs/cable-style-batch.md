# Иллюстрации кабелей по утверждённому стандарту

Этот документ дополняет CABLE_IMAGE_STYLE.md, не меняя конфигурацию и эталоны.

## Рабочая галерея и CLI

```sh
npm run images:cables:sku -- --sku YU-0000000
npm run images:cables:sku -- --sku YU-0000000 --generate
npm run images:cables:sku -- --sku YU-0000000 --bind SHA256
npm run images:cables:sku -- --sku YU-0000000 --sku YU-0000001
npm run images:cables:gallery
```

Подставьте SKU из действующей витрины. Первая команда показывает запрос без
записи файлов и обращения к API либо сообщает о сохранённом результате.
Для нового PNG используйте `--generate` после явного согласования генерации.
Команда сохранит исходный PNG и данные ревизии в `outputs/cable-sku-drafts/`.
При недостатке сведений о конструкции действие останавливается.

Найдите PNG по SHA в галерее и сохраните ручное решение с допуском для
каталога. Для назначения только одному SKU используйте `--bind` с SHA
утверждённого PNG. Готовый совместимый APPROVED можно назначить тем же способом.
Команда защищает действующие назначения и фотографии и применяет штатную
транзакцию публикации. Пакетная очередь для этого сценария не требуется.

Тот же путь доступен из рабочей галереи. Для исправления сохраните причину
в карточке PNG и используйте кнопку повторной генерации или
`--generate --retry-from SHA256`. Одно решение об исправлении допускает
одну новую попытку для исходного PNG. При неизвестном результате сетевого
запроса повтор остаётся заблокирован.

В галерее выберите визуальную группу, чтобы увидеть товары без PNG, готовые
изображения или причину блокировки генерации. Назначение готового PNG
сохраняет предыдущее утверждение. CLI и галерея используют один приоритет.
Для общей визуальной группы выбирается первый допустимый `visualKey` в
стабильном порядке. В пределах семейства при отсутствии общего ключа приоритет
имеют точный ключ и совпадение хеша профиля. Альтернативу можно выбрать по SHA.

При нескольких `--sku` команда объединяет одинаковые видимые конструкции и
последовательно вызывает тот же маршрут для одной позиции из каждой группы.
По умолчанию выполняется dry-run. Перед добавлением `--generate` нужна явная
команда на генерацию. Утверждение и назначение выполняются отдельно.

### Рабочий маршрут SKU

1. Актуальный каталог и его ручные назначения задают доступный SKU.
   `cableCatalogProfile.js` выводит видимую конструкцию из карточки и подтверждённых правил.
2. `cableReferenceCompatibility.js` определяет визуальную группу.
   Подтверждённые совпадения могут объединять разные марки. Ключи старых
   утверждений продолжают идентифицировать исходные записи.
3. `cableImageStyle.js` сначала проверяет утверждённый результат в постоянном
   реестре. Для новой конструкции готовит защищённый запрос и сохраняет PNG
   в черновик с ручной проверкой.
4. Рабочая галерея сохраняет решение по SHA. При размещении
   `cableStyleBatch.js` повторно проверяет текущий состав SKU, фотографии
   и SHA утверждения и публикует совместимые привязки в
   `shared/generatedProductImages.json`. Витрина применяет правила
   из `shared/productImages.js`.

Старые планы, отчёты и сценарии в `outputs/` остаются архивом.
Для продолжения работы заново выберите SKU в галерее или передайте список
SKU в `images:cables:sku`. Готовый PNG назначается через галерею после
проверки состава группы; старые скрипты привязки из архивов запускать не требуется.

## Записи попыток и архив

Рабочий контур читает постоянные claims и
`data/product-image-metadata/historical-generation-claims.json`. Индекс
сохраняет ключ, состояние и минимальные сведения о конструкции и SKU для
защиты от повторной оплаты после переноса архивного PNG. Рабочая галерея
открывает только известные черновики по сохранённым путям. Полный обход
старых выпусков выполняется в режиме `--archive`.

Перенос установки включает существующий индекс попыток. Для старой копии,
где индекс ещё отсутствует и исходные архивы доступны, создайте его до
первого запуска рабочего контура:

```sh
node --input-type=module -e "import {indexHistoricalCableClaims} from './scripts/lib/cableGenerationClaims.js'; await indexHistoricalCableClaims(process.cwd(), {apply:true})"
```

Резервная копия `backup:create` включает индекс и записанные резервации
из `generation-claims/`. `backup:restore` добавляет отсутствующие записи и
сохраняет резервации, которые появились позже копии. При переносе без
резервной копии скопируйте оба пути вместе с проектом. Сервис сверяет
действующие решения из реестра и постоянного журнала отдельно.

## Ручная проверка

```sh
node scripts/renderCableStyleReviews.js
```

`review-gallery.html` показывает полученные PNG на белом, тёмном и шахматном
фоне, целевой профиль, SKU, статус, отдельные флажки ручных проверок. Кнопка
экспортирует decision.json, но не меняет сайт. До генерации галерея пустая.

`recordCableStyleReview({root,draftDir,decision})` требует reviewer, точный SHA-256
и APPROVED/REJECTED. Для APPROVED все semantic checks должны быть true:
количество жил, материал, цвета, слои, направление, масштаб/пропорции, зачистка,
фон и соответствие эталону. Неуверенность — оставить NEEDS_REVIEW. Это запись
решения человека, а не автоматическое доказательство конструкции.

## Привязки после утверждения

`prepareApprovedBindingPatch` формирует проверяемый before/after patch и ничего
не применяет. `applyApprovedBindingPatch` — отдельное явно вызываемое действие:
перечитывает актуальные товары, видимые изображения и overrides; проверяет
неизменность SKU/исходных bindings, одобренный SHA PNG и текущий стандарт.
Защищает ручные/реальные изображения, блокируется общим `.pipeline.lock`.
Сохраняет новый versioned PNG и атомарно обновляет только SKU группы в
`shared/generatedProductImages.json`, записывая журнал binding-transaction.json.
Старые PNG не удаляются; historical production-v1/manifest.json не изменяется.
Если binding менялся после подготовки, применение останавливается.

Резолвер каталога допускает только точное назначение к текущей записи постоянного
реестра с `APPROVED_FOR_CATALOG=true`. При применении проверяется актуальный
профиль SKU, а статические страницы активного выпуска пересобираются перед
публикацией привязок. Импорт и восстановление применяют те же правила.
[Правила каталога и подтверждённое состояние](catalog-image-policy.md).

### Оболочки и межжильное заполнение

Контракт `construction-contract-4` передаёт генератору три независимых признака.
Наружная оболочка определяется по `hasOuterJacket`. В `technicalConstruction` из
документированного правила `data/cableTechnicalConstructionRules.json` поле
`innerSheath` содержит материал внутренней оболочки или `false` при подтверждённом
отсутствии. Поле `interstitialFilling` содержит `status` со значением `present`,
`absent` или `unknown`. Для `present` обязательны материал (`material`) и положение
(`placement`), подтверждённые источником. Пропуск поля означает `unknown`.

Внутренняя оболочка охватывает сборку жил. Изображать материал в межжильном
пространстве можно только при документированном заполнении. При подтверждённом
отсутствии заполнения границы изоляции каждой жилы остаются видимыми. При
неизвестном заполнении спорную область оставляют нераскрытой. Если разрез
должен показать эту область, сначала нужна документация производителя.
Добавление полей в контракт запроса само по себе сохраняет прежние `visualKey`.

Для ВВГнг(А)-LS-LTx 5×70 `YU-0007248` круглые многопроволочные жилы
подтверждены для принятой иллюстрации. Правило из
`data/cableReviewedIllustrationProfiles.json` применяется только при совпадении
строки источника и исходного визуального профиля. Серый внутренний слой
допущен в этой карточке как визуальное упрощение. Изображение утверждено
для каталога с `APPROVED_AS_REFERENCE=false`.

### Восстановление контекста на 11 ноября 2026

Статистика, причины блокировки, SHA и хронология находятся в секции `latest`
[журнала генерации](../data/product-image-metadata/generation-state.json).
Нормализация обозначения и практический классификатор группируют позиции в
`visualKey`. Тип визуализации выбирает один из четырёх защищённых эталонов
SIMPLE, MULTICORE, LAYERED, MULTICORE + LAYERED. `loadCableImageStyle` проверяет
конфигурацию и SHA защищённых PNG. Отдельный совместимый референс берётся из
постоянного реестра с `APPROVED_AS_REFERENCE=true`, с проверкой решения и SHA.
Контракты геометрии жил, слоёв, экрана, прилегания и зачистки передаются генератору
отдельно от стилевого эталона. Новый PNG, фактический запрос и проверка
сохраняются в папке черновика. Публикация требует отдельного решения и точной
совместимости профиля SKU. Допуск каталога не выдаёт разрешение на референс.

В сухом прогоне повторно используются явно подтверждённые поля той же
нормализованной модификации, если правило содержит источник и декларирует
соответствующее поле. Документированный контакт в одножильной конструкции
позволяет снять неизвестность внутренней оболочки только на подтверждённом
интерфейсе. Уточнения влияют на очередь, сохраняя профиль резолвера и его ключ.
Допуск по цветовому умолчанию, предположению о жиле по диапазону, соседней
марке или неизвестному заполнению не выдаётся. Номинальный диаметр, длина,
масса и точный состав пластиката вне визуально значимой разницы не являются
отдельными условиями допуска. Сечение используется для проверки исполнения
и относительных диаметров жил разных сечений. Для равных жил оно не задаёт
абсолютный масштаб иллюстрации.

По сохранённым данным уточнены отдельные поля у 77 SKU. Полностью
разблокированных SKU нет. Из 224 технически определённых SKU 192 (42 ключа)
требуют подходящего разрешённого эталона геометрии, 18 уже покрыты, 14 ждут
решения по черновикам. Свободных кандидатов для следующей партии нет.
В `blockerBreakdown` число затронутых SKU может пересекаться по причинам.
`soleBlockerSku` показывает позиции, для которых причина осталась единственной.
Сверка ранее утверждённых позиций с изменившимся профилем проводится отдельно,
без генерации по тому же ключу. Первый кандидат на расширение очереди —
группа технически определённых конструкций без подходящего эталона. Для неё
сначала нужно проверить точный охват разрешений существующих геометрических
эталонов и согласовать недостающие эталоны по геометрии.

### КГ и КГ-ХЛ: анализ и следующий запрос на согласование

Последняя пара PNG 1774×887 уже вписывается по ширине. Центр силуэта КГ
на 28 px выше середины, у КГ-ХЛ — на 17 px. Проблема сосредоточена в разлёте
четырёх концов, особенно в нижней жёлто-зелёной жиле.

| Кабель | Наклон оси | Центр концов (x, y) | Смещение центра от оси вниз | Разброс концов по x / y | Разброс поперёк оси |
| --- | ---: | --- | ---: | --- | ---: |
| КГ 4×0,75 | −10,0° | (344; 584) | 46 px | 264 / 302 px | 334 px |
| КГ-ХЛ 3×10+1×10 | −10,9° | (326; 576) | 6 px | 167 / 334 px | 360 px |

Ось измерена по серединам непрозрачного сечения наружной оболочки в правой
части кадра и экстраполирована к концам. Центры медных срезов отмечены вручную,
поэтому значения приближённые. Координаты всех четырёх концов и исходные
пути сохранены в [разметке](reports/cable-kg-composition-points-2026-11-11.json).
Прибавление поля, общий перенос и равномерное масштабирование сохраняют
относительный разлёт концов. Поворот всей картинки сохраняет этот разлёт
относительно оси и меняет контакт оболочки с правым краем. Исправление нужно
в ракурсе и расположении жил при генерации.

Предложение для следующего запроса: оставить продольный наклон около 10°,
уменьшить разворот пучка к камере и показать четыре круглые жилы компактным
ромбом или двумя смещёнными парами в глубину. Сохранить длину оголённой меди
вдоль оси каждой жилы и открытыми все четыре среза. Для этой пары на холсте
1774×887 ориентир поперечного разлёта до 220 px и смещения среднего центра
до 25 px от оси. Окончательную оценку даёт ручная проверка по срезу,
реальной укладке и перекрытиям. Ширина 80–90% желательна при целых концах и
оболочке до правой границы. У КГ-ХЛ все четыре жилы по 10 мм².
Разделитель тонкий, тёмный, матовый и неметаллический. Использовать только
защищённый эталон и отдельно разрешённый совместимый референс. Оба текущих
черновика служат для анализа ошибок. Новые запросы ждут согласования.

### Аудит передачи референсов и предконтроль композиции

Путь данных: SKU → `cableCatalogProfile.js` → визуальная группа → поиск PNG
→ при отсутствии `cableImageStyle.js` →
`cableImageProvider.js` → `POST /images/edits` → PNG и review.json →
ручное решение `cableStyleBatch.js` → постоянный реестр `cableApprovedResults.js`
→ отдельная публикация совместимых SKU → `shared/productImages.js`.

`cableApprovedStyleReference.js` читает постоянный реестр и решение рядом
с PNG. Роль геометрии требует совпадения видимой конструкции, числа и
расположения жил, оболочек, дополнительных слоёв и типа композиции.
Точное сечение и совпадение марки не могут подменять эти признаки.
Адаптер перед HTTP повторно сверяет SHA и оба разрешения. Тест с подменённым
HTTP проверяет `FormData.getAll('image[]')`, порядок, SHA обоих вложений,
endpoint и фактический промпт. В request.json сохраняются роли и SHA вложений.
Первый защищённый PNG задаёт внешний вид и кадр. Селектор добавляет
до четырёх отдельно разрешённых PNG, если они дают полезную подсказку.
Роль GEOMETRY_MATCH задаёт пространственную укладку при точном геометрическом соответствии.
Подтверждённый
технический профиль задаёт видимые материалы, цвета и слои. Типовой
многожильный запрос без второго PNG блокируется до провайдера.

У прежней пары КГ дополнительным разрешённым стилевым примером служил
трёхжильный КГ. Старый вес семейства мог пересилить число жил, а роли двух
входов не задавали воспроизводимую пространственную укладку четырёх жил.
Штатная проверка PNG измеряла альфу, края и границы силуэта. Она могла
пропустить диагональную лестницу внутри силуэта. Аудит подтверждает эти
недостатки механизма. Причину выбора конкретных пикселей моделью по журналу
API установить невозможно.

`cableMulticoreComposition.js` измеряет силуэт сразу после получения PNG.
При проверке исходного PNG разметка добавляет SHA, координаты центров срезов
и признаки целостности `ends[].complete`, число изолированных жил,
материал, исполнение и форму проводника, цвета, дополнительные проводники
и видимые роли слоёв. Программа сравнивает наблюдения с контрактом и
отмечает лишние или отсутствующие слои. Разлёт и лестница для четырёх
равных круглых жил вычисляются по координатам с нормировкой на оболочку.
Распознавание материала, формы и слоёв по пикселям здесь не заявлено.
Ручное утверждение новых черновиков требует заполненной разметки, отсутствия
ошибок и отметок по композиции. Прежние APPROVED сохраняют свои решения.

Оба черновика КГ отмечены как лестница и чрезмерный разлёт. КГ 4×0,75
также выходит за допуск по центру группы. Подходящего разрешённого
четырёхжильного геометрического референса для обоих профилей сейчас нет.
До контрольной генерации нужен выбор и явное разрешение совместимого
эталона; повторно использовать текущие черновики как референсы нельзя.
Сводка библиотеки, расчёты и состояние очереди зафиксированы в
`latest.referenceAudit` журнала генерации.

### Срез ВВГ и ВВГз

Правило `vvg-cut-quality-1` из `data/cableVvgCutQuality.json` включает
проверку плотности укладки для обычного круглого ВВГ. У ВВГз отдельно проверяется,
что заполнение видно только в межжильных промежутках у плоскости среза и не
образует выступающий рукав. Это ручные проверки конкретного PNG по SHA.
Политика не добавляет заполнитель обычному ВВГ.

Проблемные исходники идентифицируются по SHA. Их можно передать только как
точечную цель редактирования с эквивалентным профилем. Каждый исходник допускает
одно резервирование корректирующего запроса. Защищённый стилевой PNG остаётся
первым. Исходники с замечанием исключены из новых референсов, утверждений и
привязок. Действующие разрешения и назначения при этом сохраняются.

### Правила и дефекты

`data/cableIllustrationRules.json` связывает обязательные требования со
стандартами, областями применения, исполняемыми модулями и контрольными
пунктами. Генератор проверяет применимые инструкции в собранном промпте перед
резервированием. В запрос и review записываются версия, список ID и SHA правил.
Решение по новому черновику сверяется с актуальными правилами. Для действующих
утверждений сохраняются исторические условия.

`data/cableIllustrationDefects.json` хранит подтверждённые случаи и отдельно
сценарии наблюдения без подтверждённого PNG. Указанные в `hold` SHA исключаются
из новых референсов, утверждений и назначений. Только для явно зарегистрированного
исходника разрешается узкая коррекция с сохранением конструкции и исходных
привязок. Наличие проверок не означает, что модель больше не может выдать
визуальный дефект.

### Постоянные решения по PNG

`data/product-image-metadata/review-decisions/<sha256>/` хранит исходные
байты PNG, решение по SHA, профиль, visualKey, сохранённый запрос и ключ
резервирования. Штатный обзор пишет это состояние отдельно от временной
папки и HTML. Журнал читает постоянное решение первым. Отклонение и
`NEEDS_REVIEW` не дают разрешения каталогу и референсам.

Визуально утверждённый отдельный вариант можно сохранить с
`archiveOnly=true`. Он записывается в `alternativesBySha256` наравне с
архивным PNG, но не меняет действующий `byVisualKey` и
`shared/generatedProductImages.json`. Дальнейшее изменение живого
назначения требует отдельного применения.

### Импорт решений из автономной приёмки ВВГ

`node scripts/renderVvgBlockerReview.js` собирает HTML по сверке 52 профилей
от 15 ноября 2026 и текущему постоянному архиву решений. Исходные PNG встроены
в HTML без обработки. Один SHA соответствует одному решению, даже если есть
несколько исторических ключей.

1. Отметьте необходимые проверки и скачайте JSON из HTML.
2. Проверьте его командой `node scripts/importCableReviewDecisions.js decisions.json`.
3. Добавьте `--apply` для записи. Импорт обращается к обычной процедуре
   `recordCableStyleReview`. Сверка SHA, visualKey и предыдущего решения
   защищает от применения устаревшего файла.
4. Пересоберите HTML, чтобы увидеть историю. Для обновления плана выполните
   штатный dry-run.

`NEEDS_CORRECTION` сохраняет удержание профиля, `KEEP_PENDING` сохраняет
ручную проверку. Утверждение без разрешения каталога сохраняет архивный вариант.
Действующее утверждение с другим SHA требует отдельной процедуры замены.
Разрешение референса и изменение каталожной привязки выполняются отдельно.

### Контракты исправлений экранированных ВВГ и одножильного FRLS

Запрос хранит независимо `technicalProfile` (`TECHNICAL_CONTRACT`) и
`visualCompositionContract` (`VISUAL_COMPOSITION_CONTRACT`). Первый задаёт
инвентарь и порядок слоёв. Второй задаёт их видимое размещение и зачистку.
Для экранированного многожильного ВВГ действует компактная зачистка без общего
удлинения изоляции. Даже при исторической метке `LAYERED` новый запрос требует
точной многожильной геометрии и соответствующих ручных проверок.

`prepareCableStyleRequest(root, profile, { editTarget, vvgReviewRevision: true })`
готовит точечную правку только при совпадении SHA и профиля с постоянным решением
`NEEDS_CORRECTION`. Варианты исправления ограничены компактной зачисткой для
экранированного ВВГ и устранением лишней ступени у одножильного ВВГнг(А)-FRLS.
Исходник служит целью правки, допуск к положительным референсам не меняется.
Резервирование различает исходный запрос и явную редакцию по SHA источника.
Приёмка требует сравнения геометрии с исходником по `targetAnatomyPreserved`.

Контроль на реальных SKU и loopback multipart выполняет
`node scripts/verifyVvgReviewContracts.js`. Он читает зафиксированные решения,
сохраняет отправленные тела в `outputs/cable-vvg-contracts-2026-11-15/multipart-mock/`
и использует уже существующий PNG как подменный ответ только в тесте.

### Источник конструкции для новых запросов

Штатная очередь и исполнитель используют `catalog-construction-1`.
`cableCatalogProfile.js` читает SKU из локального выпуска
`data/catalog-current/products.json` и структурированные характеристики,
которые возвращает общий слой карточки товара. Для генерации этот слой
получает сохранённую расшифровку выпуска. Повторный разбор названия генератором
и расширение конструкции по правилам производителя отключены.

Отсутствующие поля отражаются в плане как `catalog-missing-or-ambiguous`,
конфликтующие как `catalog-conflict`. Наличие материала наружной оболочки
явно подтверждает наличие самой оболочки. Для неизвестного фактического
материала экрана при известных наличии и расположении действует утверждённый
символический стандарт. Нейтральная палитра относится только к изображению.

Исполнитель сверяет исходный SKU и профиль перед резервированием и запросом.
Приёмка и новые назначения сверяют актуальную конструкцию повторно. Старые
планы непригодны для выполнения. Архивные правила и данные прежних черновиков
остаются доступны для проверки истории. Прежний запрос или утверждение
удерживает новый запуск до сверки, если смена ключа скрыла прежний результат.
Действующие привязки и утверждения сохраняют прежние условия показа.

### Локальная галерея приёмки

`npm run images:cables:gallery` открывает интерфейс на
`http://127.0.0.1:4177`. Галерея работает только на loopback. Для другого порта
используйте `npm run images:cables:gallery -- --port 4180`.
`node scripts/serveCableGallery.js --inventory` формирует JSON без сервера.

Решения записываются штатной процедурой в постоянный архив по SHA. Утверждение
и допуск к совместимому использованию не выполняют привязку. Разрешение референса
хранится отдельно с именем проверяющего и историей изменений. Защищённые эталоны
и утверждённые назначения не изменяются через галерею. Снятие действующего
утверждения проходит отдельно.

Исторический PNG с проверяемым профилем можно утвердить в архиве.
Для новых каталожных назначений нужен профиль актуальной карточки.
У PNG без однозначного профиля доступны история, отклонение и исправление.
Список недостающих профилей показывает допуски и удержания, а неподтверждённые
карточки выводит отдельно с причинами. Платной генерации в интерфейсе нет.
