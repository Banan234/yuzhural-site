# Массовая генерация по утверждённому стандарту: подготовка

Этот документ дополняет CABLE_IMAGE_STYLE.md, не меняя конфигурацию и эталоны.

## Dry-run

```sh
node scripts/planCableStyleBatch.js --dry-run
```

Команда читает актуальный выпуск, результаты классификации, постоянный реестр,
разрешения референсов и назначения. Создаёт
`outputs/cable-generation-queue/queue.json` с очередью, причинами по SKU,
потенциальным охватом и хешем выпуска. Исторический dry-run в
`outputs/cable-style-batch-dry-run/` сохраняется для аудита. Доступ к API и .env
для отбора не нужен.

Фото/ручные изображения определяются консервативно: raw image, явный override,
matcher с изображением, нестандартная provenance либо видимый URL без точного
соответствия generated binding защищены. Matcher с картинкой защищает всё
соответствующее семейство, даже если его уточняющие поля ещё не проверены:
это намеренная перестраховка, не разрешение заменять фотографию.

Старые generated binding можно заменить после review. Их существование не
означает соответствие новому стандарту. Готовое изображение текущего стандарта
переиспользуется только при совпадении visualKey, версии, SHA эталона и SHA PNG.
Группа может одновременно содержать SKU с legacy-картинками и без изображения;
это один платный запрос. Количества replacement/missing ключей пересекаются.
NEEDS_REVIEW внутри смешанной группы не входит в eligibleSkus.

## Следующий этап — только после явного разрешения

Модуль `scripts/lib/cableStyleBatch.js` предоставляет:

1. `runCableStyleBatch({root, plan, cacheDir, env})` — последовательный обход.
   Новый запрос только через `generateCableStyleDraft` → `/images/edits` с PNG
   соответствующего эталона и фиксированной моделью. Пример cacheDir:
   `outputs/cable-style-batch-drafts`.
2. Каждый результат сохраняется немедленно: request.json, image.png, review.json,
   group.json с участниками SKU и batch-report.json. Одна группа = один draftKey.
3. request.json создаётся эксклюзивно до запроса. Успешный PNG при возобновлении
   декодируется и переиспользуется без API, даже если запись результата прервалась.
   Если запрос был начат, но PNG отсутствует, REQUEST_OUTCOME_UNKNOWN/FAILED:
   автоматического повторного списания нет. Проверить провайдера вручную. Гарантия
   exactly-once оплаты при потере ответа невозможна без idempotency провайдера;
   неопределённые запросы не оплачиваются повторно автоматически.
4. Одновременный запуск защищён `.batch.lock`; после аварии lock не удалять вслепую:
   сначала убедиться, что прежний процесс завершился. Claims всё равно сохраняются.
5. Повторный dry-run читает кэш: READY, CACHED_NEEDS_REVIEW, FAILED_CACHED,
   REQUEST_OUTCOME_UNKNOWN, EXISTING_STANDARD_APPROVED. Подробные причины сохранены.

## Ручная проверка

```sh
node scripts/renderCableStyleReviews.js
```

`review-gallery.html` показывает полученные PNG на белом, тёмном и шахматном
фоне, целевой профиль, SKU, статус, отдельные флажки ручных проверок. Кнопка
экспортирует decision.json, но не меняет сайт. До генерации галерея пустая.

`recordCableStyleReview({root,draftDir,decision})` требует reviewer, точный SHA-256
и APPROVED/REJECTED. Для APPROVED все semantic checks должны быть true:
количество жил, материал, цвета, слои, направление, масштаб/пропорции, зачистка,
фон и соответствие эталону. Неуверенность — оставить NEEDS_REVIEW. Это запись
решения человека, а не автоматическое доказательство конструкции.

## Привязки после утверждения

`prepareApprovedBindingPatch` формирует проверяемый before/after patch и ничего
не применяет. `applyApprovedBindingPatch` — отдельное явно вызываемое действие:
перечитывает актуальные товары, видимые изображения и overrides; проверяет
неизменность SKU/исходных bindings, одобренный SHA PNG и текущий стандарт.
Защищает ручные/реальные изображения, блокируется общим `.pipeline.lock`.
Сохраняет новый versioned PNG и атомарно обновляет только SKU группы в
`shared/generatedProductImages.json`, записывая журнал binding-transaction.json.
Старые PNG не удаляются; historical production-v1/manifest.json не изменяется.
Если binding менялся после подготовки, применение останавливается.

Резолвер каталога допускает только точное назначение к текущей записи постоянного
реестра с `APPROVED_FOR_CATALOG=true`. При применении проверяется актуальный
профиль SKU, а статические страницы активного выпуска пересобираются перед
публикацией привязок. Импорт и восстановление применяют те же правила.
[Правила каталога и подтверждённое состояние](catalog-image-policy.md).

### Оболочки и межжильное заполнение

Контракт `construction-contract-4` передаёт генератору три независимых признака.
Наружная оболочка определяется по `hasOuterJacket`. В `technicalConstruction` из
документированного правила `data/cableTechnicalConstructionRules.json` поле
`innerSheath` содержит материал внутренней оболочки или `false` при подтверждённом
отсутствии. Поле `interstitialFilling` содержит `status` со значением `present`,
`absent` или `unknown`. Для `present` обязательны материал (`material`) и положение
(`placement`), подтверждённые источником. Пропуск поля означает `unknown`.

Внутренняя оболочка охватывает сборку жил. Изображать материал в межжильном
пространстве можно только при документированном заполнении. При подтверждённом
отсутствии заполнения границы изоляции каждой жилы остаются видимыми. При
неизвестном заполнении спорную область оставляют нераскрытой. Если разрез
должен показать эту область, сначала нужна документация производителя.
Добавление полей в контракт запроса само по себе сохраняет прежние `visualKey`.

Для ВВГнг(А)-LS-LTx 5×70 `YU-0007248` круглые многопроволочные жилы
подтверждены для принятой иллюстрации. Правило из
`data/cableReviewedIllustrationProfiles.json` применяется только при совпадении
строки источника и исходного визуального профиля. Серый внутренний слой
допущен в этой карточке как визуальное упрощение. Изображение утверждено
для каталога с `APPROVED_AS_REFERENCE=false`.

### Очередь по технической готовности

`node scripts/planCableStyleBatch.js --dry-run` сохраняет актуальную очередь в
`outputs/cable-generation-queue/queue.json`. Исторический production-план
используется для сверки SKU. Его статус AUTO_APPROVED отражает допуск
к типовой иллюстрации, поэтому при новом отборе отдельно проверяются
технические признаки, подтверждённые источником. Каталоговые палитры и
предположения об исполнении жил сами по себе не дают допуск.

`READY_FOR_GENERATION` требует технически определённого профиля и подходящего
референса с отдельным разрешением. В `ALREADY_COVERED` входят действующие
назначения и точные совпадения с утверждённым PNG из реестра. При наличии
утверждения расхождение с текущим профилем требует сверки. Противоречия,
отсутствие подтверждённых данных или подходящего референса фиксируются
в `NEEDS_TECHNICAL_REVIEW`. На уровне SKU сохраняются причины и текущий статус.

Следующие запросы сортируются по числу новых уникальных SKU в выдаче, затем
по сложности конструкции. Действующие черновики актуального стандарта с
проверенным SHA ждут ручного решения и исключаются из следующей партии.
Dry-run читает сохранённые данные и выполняется без сетевых запросов.

### Восстановление контекста на 11 ноября 2026

Статистика, причины блокировки, SHA и хронология находятся в секции `latest`
[журнала генерации](../data/product-image-metadata/generation-state.json).
Нормализация обозначения и практический классификатор группируют позиции в
`visualKey`. Тип визуализации выбирает один из четырёх защищённых эталонов
SIMPLE, MULTICORE, LAYERED, MULTICORE + LAYERED. `loadCableImageStyle` проверяет
конфигурацию и SHA защищённых PNG. Отдельный совместимый референс берётся из
постоянного реестра с `APPROVED_AS_REFERENCE=true`, с проверкой решения и SHA.
Контракты геометрии жил, слоёв, экрана, прилегания и зачистки передаются генератору
отдельно от стилевого эталона. Новый PNG, фактический запрос и проверка
сохраняются в папке черновика. Публикация требует отдельного решения и точной
совместимости профиля SKU. Допуск каталога не выдаёт разрешение на референс.

В сухом прогоне повторно используются явно подтверждённые поля той же
нормализованной модификации, если правило содержит источник и декларирует
соответствующее поле. Документированный контакт в одножильной конструкции
позволяет снять неизвестность внутренней оболочки только на подтверждённом
интерфейсе. Уточнения влияют на очередь, сохраняя профиль резолвера и его ключ.
Допуск по цветовому умолчанию, предположению о жиле по диапазону, соседней
марке или неизвестному заполнению не выдаётся. Номинальный диаметр, длина,
масса и точный состав пластиката вне визуально значимой разницы не являются
отдельными условиями допуска. Сечение используется для проверки исполнения
и относительных диаметров жил разных сечений. Для равных жил оно не задаёт
абсолютный масштаб иллюстрации.

По сохранённым данным уточнены отдельные поля у 77 SKU. Полностью
разблокированных SKU нет. Из 224 технически определённых SKU 192 (42 ключа)
требуют подходящего разрешённого эталона геометрии, 18 уже покрыты, 14 ждут
решения по черновикам. Свободных кандидатов для следующей партии нет.
В `blockerBreakdown` число затронутых SKU может пересекаться по причинам.
`soleBlockerSku` показывает позиции, для которых причина осталась единственной.
Сверка ранее утверждённых позиций с изменившимся профилем проводится отдельно,
без генерации по тому же ключу. Первый кандидат на расширение очереди —
группа технически определённых конструкций без подходящего эталона. Для неё
сначала нужно проверить точный охват разрешений существующих геометрических
эталонов и согласовать недостающие эталоны по геометрии.

### КГ и КГ-ХЛ: анализ и следующий запрос на согласование

Последняя пара PNG 1774×887 уже вписывается по ширине. Центр силуэта КГ
на 28 px выше середины, у КГ-ХЛ — на 17 px. Проблема сосредоточена в разлёте
четырёх концов, особенно в нижней жёлто-зелёной жиле.

| Кабель | Наклон оси | Центр концов (x, y) | Смещение центра от оси вниз | Разброс концов по x / y | Разброс поперёк оси |
| --- | ---: | --- | ---: | --- | ---: |
| КГ 4×0,75 | −10,0° | (344; 584) | 46 px | 264 / 302 px | 334 px |
| КГ-ХЛ 3×10+1×10 | −10,9° | (326; 576) | 6 px | 167 / 334 px | 360 px |

Ось измерена по серединам непрозрачного сечения наружной оболочки в правой
части кадра и экстраполирована к концам. Центры медных срезов отмечены вручную,
поэтому значения приближённые. Координаты всех четырёх концов и исходные
пути сохранены в [разметке](reports/cable-kg-composition-points-2026-11-11.json).
Прибавление поля, общий перенос и равномерное масштабирование сохраняют
относительный разлёт концов. Поворот всей картинки сохраняет этот разлёт
относительно оси и меняет контакт оболочки с правым краем. Исправление нужно
в ракурсе и расположении жил при генерации.

Предложение для следующего запроса: оставить продольный наклон около 10°,
уменьшить разворот пучка к камере и показать четыре круглые жилы компактным
ромбом или двумя смещёнными парами в глубину. Сохранить длину оголённой меди
вдоль оси каждой жилы и открытыми все четыре среза. Для этой пары на холсте
1774×887 ориентир поперечного разлёта до 220 px и смещения среднего центра
до 25 px от оси. Окончательную оценку даёт ручная проверка по срезу,
реальной укладке и перекрытиям. Ширина 80–90% желательна при целых концах и
оболочке до правой границы. У КГ-ХЛ все четыре жилы по 10 мм².
Разделитель тонкий, тёмный, матовый и неметаллический. Использовать только
защищённый эталон и отдельно разрешённый совместимый референс. Оба текущих
черновика служат для анализа ошибок. Новые запросы ждут согласования.

### Аудит передачи референсов и предконтроль композиции

Путь данных: SKU → `familyVisualRules.js` / `cableVisualClassification.js` →
`visualKey` и очередь `cableGenerationQueue.js` → `cableImageStyle.js` →
`cableImageProvider.js` → `POST /images/edits` → PNG и review.json →
ручное решение `cableStyleBatch.js` → постоянный реестр `cableApprovedResults.js`
→ отдельная публикация совместимых SKU → `shared/productImages.js`.

`cableApprovedStyleReference.js` читает постоянный реестр и решение рядом
с PNG. Роль геометрии требует совпадения видимой конструкции, числа и
расположения жил, оболочек, дополнительных слоёв и типа композиции.
Точное сечение и совпадение марки не могут подменять эти признаки.
Адаптер перед HTTP повторно сверяет SHA и оба разрешения. Тест с подменённым
HTTP проверяет `FormData.getAll('image[]')`, порядок, SHA обоих вложений,
endpoint и фактический промпт. В request.json сохраняются роли и SHA вложений.
Один защищённый PNG задаёт внешний вид и кадр. Второй задаёт пространственную
укладку только при точном геометрическом соответствии. Подтверждённый
технический профиль задаёт видимые материалы, цвета и слои. Типовой
многожильный запрос без второго PNG блокируется до провайдера.

У прежней пары КГ дополнительным разрешённым стилевым примером служил
трёхжильный КГ. Старый вес семейства мог пересилить число жил, а роли двух
входов не задавали воспроизводимую пространственную укладку четырёх жил.
Штатная проверка PNG измеряла альфу, края и границы силуэта. Она могла
пропустить диагональную лестницу внутри силуэта. Аудит подтверждает эти
недостатки механизма. Причину выбора конкретных пикселей моделью по журналу
API установить невозможно.

`cableMulticoreComposition.js` измеряет силуэт сразу после получения PNG.
При проверке исходного PNG разметка добавляет SHA, координаты центров срезов
и признаки целостности `ends[].complete`, число изолированных жил,
материал, исполнение и форму проводника, цвета, дополнительные проводники
и видимые роли слоёв. Программа сравнивает наблюдения с контрактом и
отмечает лишние или отсутствующие слои. Разлёт и лестница для четырёх
равных круглых жил вычисляются по координатам с нормировкой на оболочку.
Распознавание материала, формы и слоёв по пикселям здесь не заявлено.
Ручное утверждение новых черновиков требует заполненной разметки, отсутствия
ошибок и отметок по композиции. Прежние APPROVED сохраняют свои решения.

Оба черновика КГ отмечены как лестница и чрезмерный разлёт. КГ 4×0,75
также выходит за допуск по центру группы. Подходящего разрешённого
четырёхжильного геометрического референса для обоих профилей сейчас нет.
До контрольной генерации нужен выбор и явное разрешение совместимого
эталона; повторно использовать текущие черновики как референсы нельзя.
Сводка библиотеки, расчёты и состояние очереди зафиксированы в
`latest.referenceAudit` журнала генерации.
