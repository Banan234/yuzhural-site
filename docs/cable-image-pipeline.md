# Изображения кабелей: одна визуальная группа — один PNG

## Production, этап 1: утверждённые 446 новых visualKey

Пользователь разрешил 119 REUSE / 570 SKU и 446 MISSING / 1307 SKU из
принятого практического dry-run. 3831 NEEDS_REVIEW исключены из очереди.

```sh
npm run images:cables:production -- --prepare
npm run images:cables:production -- --run
npm run images:cables:production -- --status
```

`--prepare` проверяет ровно утверждённый объём и SHA-256 всех 815 защищённых
файлов принятого аудита. Он сохраняет неизменяемый план в
`data/product-image-metadata/production-v1/plan.json`; API не вызывается.
После старта для продолжения используется `--run`, без повторной подготовки.

Генератор использует существующий `cableImageProvider.js`, отдельный
`IMAGE_API_KEY` из `.env`, `https://codex.sale/v1/images/generations` и
`gpt-image-2.5-flare`. Авторизация подписки Codex не используется. В manifest
попадают только разрешённые параметры рендера, без ключа и заголовков.

Prompt строится из замороженного `visualProfile`: отдельные правила для
провода без общей оболочки, скрученного СИП, плоского кабеля, solid/stranded,
металла, цветов, ленточной/проволочной брони, общего экрана, дренажа и
огнестойкого барьера. Масштаб компактный, небольшой сдвиг вправо; увеличение
объекта и обязательное заполнение кадра не задаются. Старые PNG не меняются.

Два контролируемых worker сохраняют исходный PNG сразу после ответа, затем
проверяют декодирование/CRC, alpha и реальную прозрачность. Фактическое
разрешение не обязано совпадать с запрошенным. Сохраняются metadata группы
со всеми SKU и сечениями, checkpoint и привязки. Запись JSON атомарная,
изменения SKU manifest сериализованы. Общая блокировка совместима со старым
генератором. Исходный каталог не записывается.

Авторитетный production manifest:
`data/product-image-metadata/production-v1/manifest.json`.
Файлы каждой группы: `production-v1/groups/<visualKey>.json`.
Новые PNG: `public/product-images/generated/pr1_<visualKey>.png`.
Журнал и отчёт: `outputs/cable-image-production-2026-10-16`.

При повторном запуске валидные сохранённые PNG используются без API.
PNG, сохранённый перед прерыванием, восстанавливается из checkpoint.
Блокировка завершившегося локального процесса снимается только после проверки
hostname и отсутствия PID; активный процесс или другая машина запрещают запуск.
Запрос с неопределённым исходом и без файла не повторяется автоматически:
он остаётся FAILED, чтобы не списать деньги повторно. Ограниченные retry
временных API-ошибок выполняет существующий адаптер. Ошибки одной группы
сохраняются и не мешают следующим. Эстетических повторов нет.

Визуальные ошибки количества жил фиксируются в
`shared/rejectedProductImages.json`; карточки сразу исключают такие изображения.
После завершения worker команда
`node scripts/checkCableVisualProduction.js --finalize-quality` снимает только
их новые привязки, сохраняет PNG как свидетельство и ставит FAILED в production
manifest. Повторный запуск не генерирует и не назначает отклонённые результаты.
Проверка также доказывает сохранность исходного каталога, старых PNG и всех
NEEDS_REVIEW, проверяет фактическое разрешение привязок штатным frontend helper
и создаёт HTML-галерею выборки конструкций и всех новых изображений.

## Текущий этап: практический dry-run, без генерации

На 16 октября 2026 пользователь утвердил 119 существующих PNG по стилю и типажу.
Актуальный аудит использует `data/familyVisualRules.json`: централизованные
правила известных семейств и явно обозначенные **каталоговые** defaults.
Они не переписывают фактические характеристики SKU. Строгий профиль остаётся
в `technicalProfile`; подставленные визуальные соглашения — в
`illustrationDefaults`, разрешённые пробелы данных — в `nonBlockingIssues`.

```sh
npm run images:cables:audit
# Предыдущий строгий режим при необходимости:
node scripts/auditCableVisuals.js --dry-run --strict --out outputs/cable-visual-strict-comparison
```

Практический результат сохраняется отдельно в
`outputs/cable-visual-practical-2026-10-16`. Прежний отчёт остаётся исторической
базой сравнения (5404 NEEDS_REVIEW).

**Критические признаки:** семейство и тип изделия, количество проводников,
материал/строение/форма проводника, круглая/плоская/скрученная конструкция,
наличие общей оболочки, броня и экран, специальные видимые слои.
Явные противоречия, неизвестные модификаторы, парные/коаксиальные/оптические
конструкции без отдельного правила остаются NEEDS_REVIEW.

**Не блокируют:** неизвестный заполнитель, точный состав полимера и диаметр,
визуальная толщина по сечению, фактическое назначение N/PE при наличии
согласованной каталоговой палитры. Явно известные цвета/PE/N не затираются
defaults. Установка цвета или `solid` для иллюстрации не утверждает такого
исполнения у конкретной партии. Документированные переходы конструкции жилы
по сечению ПуВ/ПВ1 сохраняются.

`REUSE` проверяет совпадение критических видимых признаков с утверждённым PNG;
отсутствие новых некритических metadata у старого файла ему не мешает.
Разный материал, количество жил, плоское исполнение, экран, броня, известная
многопроволочность или цвет оболочки запрещают неверное сопоставление.
`autoApprovedSkus` и `reviewSkus` группы разделены: конфликт одного SKU не
распространяется на остальные, а сам конфликтный SKU не получает картинку.

Команда по-прежнему допускает только dry-run: image provider и `.env` не
используются; PNG и привязки не записываются. Результат содержит статистику,
20 AUTO_APPROVED групп разных семейств, 20 NEEDS_REVIEW с причинами и полный
состав всех групп. `MISSING` — предложение для следующего согласования,
не разрешение запускать старый генератор по этому списку.

Ниже сохранено описание предыдущих этапов и старого генератора.

Pipeline сначала разбирает **весь** каталог, вычисляет `visualKey` и группирует SKU.
Только после этого применяет выбор и лимит, проверяет кэш и составляет очередь.
Одна группа создаёт одно задание генерации, независимо от количества её SKU.
Проверенное изображение привязывается ко всем подходящим товарам группы.

Сечение сохраняется у каждого SKU, но по умолчанию не влияет ни на ключ, ни на
геометрию, ни на prompt. Пример:

```text
ВВГнг(А)-LS 3х1.5 ─┐
ВВГнг(А)-LS 3х2.5 ─┼─ vvgnga-ls__3core → vvgnga-ls__3core.png
ВВГнг(А)-LS 3х4   ─┤
ВВГнг(А)-LS 3х6   ─┘
```

## Правила группировки

`getCableVisualConfig` / `getCableVisualKey` в `scripts/lib/cableImageVisual.js`
отделены от парсинга, API и очереди. Настройки находятся в
`data/cableImageConfig.json → visualRules`.

В ключ входят семейство **с индексами исполнения**, число жил, форма, материал,
тип проводника (однопроволочный/многопроволочный), оболочка и упорядоченные цвета
жил. Базовые свойства подразумеваются пресетом семейства; отличия получают суффиксы:

| Конструкция                  | Пример ключа                   |
| ---------------------------- | ------------------------------ |
| ВВГнг(А)-LS, 3 жилы          | `vvgnga-ls__3core`             |
| ВВГнг(А)-LS, 4 жилы          | `vvgnga-ls__4core`             |
| Плоский ВВГнг(А)-LS, 3 жилы  | `vvg-pnga-ls__3core`           |
| ПВС, белая оболочка, 3 жилы  | `pvs__3core`                   |
| ПВС, чёрная оболочка, 3 жилы | `pvs__3core__jacket-black-pvc` |

Разные семейства и индексы не объединяются по одному лишь количеству жил.
Неизвестный модификатор, броня, экран, огнестойкий барьер, HF, парная/сложная
конструкция или отсутствие точной цветовой схемы приводят к пропуску с причиной.
Пресеты пока охватывают ВВГ, ВВГ-П, АВВГ, АВВГ-П, КГ, ПВС, КВВГ и явно разрешённые
индексы, с цветовыми профилями до пяти жил. Это не покрытие всего прайса.
Новые семейства требуют отдельных проверенных пресетов.

SKU, артикул, цена, длина и остаток не входят в ключ.
Отдельный `render_fingerprint` учитывает prompt, провайдера/base URL, endpoint, модель, запрошенный размер, качество, формат,
фон, настройки canvas и референс (только для edits). Изменение этих настроек не меняет человеческое имя группы. При
`preserveApprovedVisuals: true` уже одобренный совместимый visualKey сохраняет
свой PNG и фактическую provenance даже при смене шаблона/модели. Неодобренный
устаревший кэш требует решения; автоматической повторной генерации нет.
Полный дескриптор конструкции сохраняется и проверяется на коллизии ключей.

`groundCores` существующего парсера означает дополнительную группу NxS:
на изображении используется суммарное количество жил; основное и дополнительное
сечения остаются в metadata. Само NxS не доказывает назначение N/PE.
Цвета из `data/cableImageColors.json` — каталожная условность; подтверждённые
исключения задаются в `skuOverrides`. Перед привязкой нужен просмотр конструкции.

В metadata группы (`schemaVersion: 2`) есть `visualKey`, `family`, `cores`,
`sectionAffectsVisual`, `image`, `products`, prompt, фактические provider/model,
`createdAt`, статус, checksum и результат просмотра. Каждый элемент `products`
содержит SKU, название, ID, сечение, дополнительное сечение, разобранные параметры
и fingerprint товара. Снимки по SKU сохраняют его собственное сечение.

Каталог берётся из `data/catalog-current/products.json`; переопределение:
`--catalog PATH` → `CATALOG_PRODUCTS_FILE` → конфигурация. Поддерживаются массив
и `{ "items": [] }`. Противоречивые поля/названия пропускаются, дубли SKU запрещены.
Импорт, исходный прайс и реестр SKU не изменяются.

## Обязательный dry-run

Нужны Node.js 22+ и зависимости `npm ci`. Dry-run не требует API-ключа, не создаёт
блокировку, metadata, PNG или привязки. Перенаправление stdout сохраняет только отчёт.

```bash
# Весь каталог; чистый JSON без служебной шапки npm:
node scripts/generateCableImages.js --dry-run --json > outputs/cable-image-plan.json

# Одна группа, включая все её SKU:
node scripts/generateCableImages.js --sku YU-0000815 --dry-run --json > outputs/pilot-plan.json
```

В отчёте:

- `total_skus`, `skus_without_images`: весь каталог, без учёта картинок категорий;
- `parsed_skus`, `unsupported_skus`: покрытие подтверждёнными пресетами;
- `unique_visual_groups`: группы по всем поддержанным SKU;
- `selected_visual_groups`, `selected_skus`: область после фильтров;
- `existing_group_images`: найденные и проверенные PNG выбранных групп;
- `new_images_required`, `api_requests_planned`: одно новое изображение/первичный
  запрос на отсутствующую выбранную группу;
- `maximum_api_attempts`: верхняя граница с повторами при временных ошибках;
- `api_requests_executed: 0`: в dry-run запросов нет;
- `blocked_groups`, `pending_review_groups`: группы, которым требуется решение;
- `groups`: все SKU/сечения, дескриптор, действие, существующий/ожидаемый путь, prompt;
- `skipped`: причины для неподдержанных и сохранённых позиций.

**`--limit` теперь ограничивает группы, не SKU.** `--sku` выбирает целые группы.
`--sort stock` упорядочивает группы по максимальному остатку участника; это не продажи.
Без фильтров dry-run показывает весь каталог. Обычный запуск дополнительно требует
`--sku`, `--limit` или `--all` и совпадающий сохранённый dry-run через `--plan`.
Изменение состава, ключевых параметров или кэша делает план устаревшим и останавливает
работу до создания нового dry-run, до обращения к провайдеру.

## Будущий запуск после отдельного подтверждения

В рамках изменения группировки выполняется **только dry-run**. Следующие команды
описывают будущий ручной запуск после подтверждения пользователем:

```bash
node scripts/generateCableImages.js --sku YU-0000815 --plan outputs/pilot-plan.json
```

### codex.sale и отдельный ключ

Настройки берутся из локального `.env` (игнорируется Git):

```dotenv
IMAGE_API_BASE_URL=https://codex.sale/v1
IMAGE_API_KEY=<отдельный ключ codex.sale>
IMAGE_MODEL=gpt-image-2.5-flare
```

`.env.example` содержит только пустой ключ. Переменные не имеют префикса `VITE_`
и не передаются в браузер. `IMAGE_API_BASE_URL` и `IMAGE_MODEL` переопределяют JSON.
`IMAGE_API_KEY` читается адаптером только при запросе и не сохраняется в config,
metadata или отчётах. Авторизация текущего Codex/ChatGPT и `OPENAI_API_KEY` не
используются. Без отдельного ключа вызов завершается ошибкой.

По умолчанию `provider: "codex-sale"`, `imageEndpoint: "generations"`: POST
`https://codex.sale/v1/images/generations`, JSON с `model`, `prompt`, `n: 1`,
`size`, `quality`, `background: "transparent"`, `output_format: "png"`.
Наличие локального референса **не переключает** endpoint на edits. Для отдельного
провайдера с поддержкой редактирования можно явно включить `imageEndpoint: "edits"`.
Тогда только и отправляется референс multipart-запросом.

Flare в `.env` — запрошенная пользователем настройка, а не автоматически выбранный
победитель сравнения. Каталожная генерация остаётся за обязательным dry-run/plan.

Для картинки из другого инструмента есть ingest, тоже по одной группе и сохранённому плану:

```bash
node scripts/generateCableImages.js ingest --sku SKU --plan outputs/pilot-plan.json \
  --image /absolute/result.png --source-provider NAME --source-model NAME
```

API-адаптер делает `n=1` для каждого задания группы. Endpoint выбирается явно. Таймаут и повтор HTTP 408/429/5xx ограничены настройками.
Постоянные 4xx/невалидный PNG не перегенерируются автоматически. Повторы после
потери ответа могут приводить к дополнительным списаниям; число попыток сохраняется.
Фактический provider/model результата хранится отдельно от запрошенной API-модели.

## Просмотр, привязка и восстановление

Переходы: `generating → needs_review → approved` или `failed`, по **группе**.
Даже непроверенный PNG кэшируется на всю группу: второй SKU не запускает генерацию.
Техническая проверка: непустой валидный PNG, декодирование/CRC, положительные
фактические размеры, допустимое число пикселей и alpha-канал при transparent.
**Несовпадение фактического и запрошенного размера не является ошибкой.**
Фактические размеры, alpha и прозрачность сохраняются в metadata.
Площадь объекта, прозрачность фона и поля возвращаются как `warnings`, не вызывают
повторную платную генерацию. Наличие alpha и наличие прозрачных пикселей —
отдельные поля; непрозрачный RGBA может иметь alpha-канал без прозрачного фона.
Количество/цвета жил, направление, фон и полнота геометрии проверяются просмотром.

Опциональная локальная нормализация в `cableImageConfig.json`:

```json
"normalization": { "enabled": true, "width": 1536, "height": 1024 }
```

Метод `contain`: пропорционально вписать исходный PNG в прозрачный canvas,
без растягивания. Для нового стиля с правым обрезом результат выравнивается
по правому краю, чтобы нормализация не добавила там прозрачный зазор. Интерполяция учитывает alpha. В `source_validation`
сохраняются размеры/checksum исходного ответа, в `validation` — конечного PNG;
в `normalization` — параметры преобразования. По умолчанию выключена.
Сравнительные тестовые PNG всегда сохраняются в исходном размере, без нормализации.

Финальный стиль `right-edge-solid-v2`:

- Цельная оболочка входит **через правую границу** и намеренно уходит за кадр.
  Справа нет видимого торца, заглушки или прозрачного зазора.
- Все металлические концы слева видны целиком, с небольшим одинаковым отступом.
  Верх и низ остаются с безопасным полем; огромных пустых полей нет.
- Общая ось оболочки поднимается к правому краю с фиксированным небольшим уклоном
  8°, преимущественно горизонтально. Переход к жилам около 56% ширины, левые
  концы около 6%; сверху/снизу ориентир 10%.
- По умолчанию `visualRules.default.conductorConstruction: "solid"`: одна цельная
  круглая проволока в каждой жиле, `solid-core copper conductors`, без пучков.
  Это стандарт иллюстрации, не техническое утверждение для всего прайса.
- Достоверная маркировка мж/мк/мс имеет приоритет. Для КГ и ПВС сохранены отдельные
  правила `conductorConstruction: "stranded"` из существующих пресетов гибкой
  конструкции. Противоречивые признаки пропускаются. Для алюминия металл серебристый.
- Точное число и настроенные цвета жил повторяются в общем prompt builder.
  Формулировки о необходимости показать правый торец целиком удалены.
- PNG прозрачен, без текста, маркировок, логотипов, свечения и фоновых ореолов.

Pixel-проверка считает `touches_right_edge` и `right_edge_foreground_ratio`.
Правый обрез не считается ошибкой отступа; проверка полей остаётся слева/сверху/
снизу. Зазор справа становится предупреждением для просмотра, без платного retry.

После просмотра сохраните JSON:

```json
{
  "cores": 3,
  "colors": ["brown", "blue", "yellow-green"],
  "orientation": "right-to-left",
  "rightEdgeCropped": true,
  "leftUncropped": true,
  "topBottomClear": true,
  "conductorConstruction": "solid",
  "noText": true,
  "styleMatches": true,
  "reviewer": "имя проверившего"
}
```

```bash
node scripts/generateCableImages.js approve --sku SKU --review review.json
# Несколько просмотренных групп, без генерации:
node scripts/generateCableImages.js approve-batch --review batch-reviews.json
```

`batch-reviews.json`: `{ "reviews": [{ "visualKey": "...", "review": { ... } }] }`.
Каждая группа проверяется и привязывается отдельно; ошибка одного review записывается,
остальные продолжаются. Подтверждения количества/цветов/конструкции/ракурса заполняются
после просмотра, не автоматически из prompt. Неверное число жил остаётся needs_review;
слабое отличие от референса не запускает новую генерацию.

Одобрение по любому SKU проверяет всю группу и связывает **всех актуальных
подходящих участников** с одним PNG, с отдельным сечением каждого SKU.
Индивидуальные фотографии/overrides сохраняются по умолчанию.
`getProductImage` использует реестр в каталоге, карточке и SEO; привязки переживают
импорт прайса. Одобрение повторяемо и восстанавливает реестр после прерывания.

`failed`, `generating`, повреждённый PNG, устаревший render fingerprint и файл без
metadata блокируют скрытую повторную генерацию. `--force` требует нового dry-run,
создаёт `-v2`, `-v3`, архивирует metadata и сохраняет старую привязку до новой проверки.
`--force` и `--missing-only` несовместимы. Одна блокировка исключает параллельные
процессы; concurrency ограничивает число групп внутри процесса. После аварии
проверьте PID из `.pipeline.lock` перед ручным удалением блокировки.

Старый одобренный пилот распознаётся по точному fingerprint товара, старому render
fingerprint и checksum PNG. Dry-run показывает его как существующий, **не переносит
файлы и не меняет привязки**. Будущий запуск reuse сохранит исходное имя PNG,
истинные prompt/provider/model и создаст metadata группы без новой генерации.
Все новые PNG называются по `visualKey`.

Production-публикация отдельная: нужны frontend/SSR сборка, доставка PNG/metadata/
реестра и перезапуск backend. Pipeline сам не выкладывает сайт.

## Зависимость от сечения в будущем

Сейчас `visualRules.default.sectionAffectsVisual` равно `false`. Можно включить
зависимость только у выбранного семейства:

```json
{
  "visualRules": {
    "default": { "sectionAffectsVisual": false },
    "families": { "ВВГнг(А)-LS": { "sectionAffectsVisual": true } }
  },
  "geometry": {
    "sectionMode": "bands",
    "defaultThickness": "uniform catalogue scale",
    "sectionBands": [
      { "maxSection": 6, "label": "standard visual thickness" },
      { "maxSection": 1000, "label": "visually thicker conductors" }
    ]
  }
}
```

Это фрагмент настройки: остальные `visualRules` нужно сохранить. Семейства без
флага продолжают игнорировать сечение даже при наличии диапазонов.
При `sectionAffectsVisual: true` и `constant` ключ различает точные сечения;
при `bands` — качественные диапазоны. Расчёт физического диаметра не используется.

## Сравнение четырёх моделей без привязки к каталогу

```bash
# Только план, без запросов:
npm run images:cables:models

# Ровно по одному запросу на четыре модели, только по явному разрешению:
npm run images:cables:models -- --run --out outputs/codex-sale-image-models-2026-10-15
```

Фиксированный список: `gpt-image-2.5-sunburst`, `gpt-image-2.5-flare`,
`gpt-image-2`, `gpt-image-1.5`. Для всех используется один и тот же prompt/размер/
качество/фон, без референса. Prompt и SHA-256 сохраняются в папку результатов.
`retries=0`; перед запросом его слот сохраняется как `requesting`.
Повторный запуск с той же папкой не повторяет `requesting`, `failed` или `success`
слоты, даже после прерывания. Статусы и HTTP-коды сохраняются в `report.json`.
Если статус requesting остался после аварии, результат неизвестен и новый платный
запрос не отправляется. Глобальная для этой папки блокировка исключает два запуска.

Имена файлов: `test-sunburst.png`, `test-flare.png`, `test-image-2.png`,
`test-image-1.5.png`. Сохраняются сырые PNG, реальные размеры, размер файла,
alpha/прозрачность и HTTP status. Победитель не выбирается.
Скрипт не читает каталог, не вызывает approve, не пишет `public/`, товарную metadata
или реестр привязок. Для отсутствующей alpha результат сохраняется для сравнения
с отметкой об отсутствии alpha, без дополнительных запросов.

# Аудит конструкций перед следующим запуском (16 октября 2026)

Текущие опубликованные в локальном каталоге PNG считаются визуальным стандартом.
Новый этап классификации **не изменяет** стиль, prompt builder, масштаб, файлы
изображений и действующие привязки. Он не импортирует image provider, не читает
`.env` и не делает сетевых запросов.

```sh
npm run images:cables:audit -- --out outputs/cable-visual-audit-2026-10-16
```

Отдельная точка входа `scripts/auditCableVisuals.js` допускает только `--dry-run`.
Правила находятся в `data/cableVisualClassificationRules.json`; технические
источники — там же и в существующей базе `shared/designationKnowledgeBase.json`.
Приоритет: исходное название + структурированные характеристики → точное
нормализованное семейство → документированное правило → ручная проверка.
Исходные названия сохраняются буквально. Разные пробелы и записи `нг А LS`
нормализуются; отсутствующая категория А автоматически не добавляется.

`visualProfile` содержит тип изделия, материал/строение/форму проводника,
геометрию, общую оболочку и её материал/цвет, экран/броню и их типы, заполнитель,
цвета и PE/N, дополнительные элементы и конфигурацию жил. Полный профиль
участвует в `visualKey` (читаемый префикс + SHA-256 идентичности). Это **новые
аналитические ключи**: старые имена PNG и metadata не переименовываются.

Количество жил не доказывает наличие PE/N. Старый `hasGroundCore=false` означает
результат разбора, а не отсутствие защитной жилы. Синий цвет не доказывает функцию
N. Каталоговая палитра прежнего генератора не считается доказательством для SKU.
Неизвестная конструкция не заменяется прежним визуальным стандартом `solid`.

Сечение сохраняется в каждой строке отчёта и по умолчанию не разделяет группы.
Исключения задаются `constructionBands` (подтверждённая смена строения, например
ПуВ/ПВ1) или `sectionAffectsVisual` + `visualSectionBands` в `familyOverrides`.
Физический диаметр по площади сечения не рассчитывается.

- `recognized`, confidence `high`/`medium`: обязательные признаки определены.
- `needs_review`, confidence `low`: есть неизвестные признаки, конфликт или
  неподдержанная специальная конфигурация; автоматическая привязка запрещена.
- `REUSE`: профиль совместим с описанием утверждённого изображения.
- `MISSING`: полный профиль, подходящего утверждённого изображения нет.
- `NEEDS_REVIEW`: классификация или соответствие существующей картинке неоднозначно.

Старые изображения описываются по имеющимся metadata, с сохранением исходного
ключа, пути и SHA-256. Отсутствующие сведения (например, заполнитель) остаются
неизвестными. Наличие уже назначенной картинки не повышает confidence SKU.

Отчёт включает HTML с поиском/фильтрами и составом каждой группы, CSV всех SKU,
полный JSON, отдельные JSON ручной проверки, групп и существующих изображений.
Контрольные суммы каталога, PNG, всех metadata, manifest и прежних настроек
проверяются до и после анализа. Счётчики `apiRequests`, `imagesGenerated`,
`bindingsChanged` равны нулю. Аналитический отчёт нельзя передать старому
генератору как утверждённый план. После просмотра групп нужен отдельный этап
их утверждения; на этом этапе ничего генерировать или массово назначать нельзя.
